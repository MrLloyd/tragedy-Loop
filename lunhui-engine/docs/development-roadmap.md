## 开发目标与范围

第一版交付可以在一台电脑上创建剧本、轮流操作各席位、完成整局、保存恢复和复现问题的版本。单机初期采用同机轮流操作，并提供独立的全知调试模式。电脑对手属于后续功能：单机版本不默认包含自动扮演剧作家或主人公的 AI。

沿用当前 TypeScript 工程和已有引擎接口。界面显示状态、收集选择并提交命令；发动资格、目标合法性、结算和胜负由引擎决定。正式 UI 的具体组件选型在读取既有框架约定后确定。

## P0：建立逐条规则验收清单

状态：2026-09-26 已完成来源盘点与实现/测试定位，交付见 [content-audit.md](content-audit.md)。确认 3 项行为问题和 1 项公开视图字段缺口；详细语义验收与修复继续按 P1/P3 推进。

交付物：`docs/content-audit.md`，按附录 B、附录 C 和流程图建立完整清单。

每项记录规则原文位置、模组、角色或身份、时点、条件、选择者、合法对象、实际与有效数量口径、效果顺序、限次、公开信息边界、代码位置、测试位置和验收状态。一段文字含多个独立能力时拆开记录；不同模组同名但文本不同的条目分别核对。

验收状态使用：待核对、缺实现、实现待修正、实现已核对但测试不足、专项测试通过、对局联调通过。已经存在实现的项目直接复用并验证。

覆盖范围包括：角色特性、友好能力、身份特性与能力、常驻、规则 Y/X、特殊规则、事件、剧本配置约束和跨轮回效果。制作时约束也要入表，不能只统计主动技能。逐条确认历史流程裁定；新增歧义记录冲突文本和受影响行为，再向用户询问。

完成标准：源文档中的每项具体规则均有对应行和明确状态；尚未核对的项目保留待核对状态。登记数量或非空处理器不能自动标为验收通过。

## P1：先验收 First Steps 完整对局

选择一个配置合法、内容范围清楚的 First Steps 剧本作为首个可交付目标。验收该剧本使用的角色技能、身份能力、事件和规则，并准备其他场景覆盖 First Steps 中未被该剧本使用的条目。

按规则逐项断言：技能是否应该出现在菜单、谁负责选择、目标范围、实际效果、限次是否消耗、后续强制是否触发、是否影响当前轮回，以及各席位能看到什么。

关键场景至少包括：杀手杀死关键人物、死亡保护改变结果、亲友死亡及下轮处理、杀人狂人数条件、友好能力拒绝与限次、事件未发生与完成结算的区别、强制后续与立即结束的顺序。选择等待点应验证保存恢复不会改变选择者、候选项或结果。

完成标准：First Steps 每项规则拥有与文本对应的结果断言；至少一套合法剧本从开局到最终结果通过引擎正常接口完成，另有场景验证不同的胜负与跨轮路径。直接设置状态的单元测试可用于边界验证，但不能替代正常开局的整局测试。

## P2：制作单机调试界面

P1 达标后接入简单可操作界面，用于发现真实操作中的遗漏。其余模组可在开发模式中保留入口，玩家模式明确显示已验收范围。

| 页面或区域 | 必须支持的操作和信息                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| 开局配置   | 加载合法示例剧本；选择模组、角色、身份、规则、事件和必要参数；显示具体配置错误   |
| 对局主界面 | 轮回、日期、阶段、队长、版图、角色状态、指示物、当前席位手牌、公开事件表和日志   |
| 待选择区域 | 引擎给出的行动、技能、对象、选项、选择数量和确认操作；所有等待类型均有可操作入口 |
| 席位切换   | 剧作家和三位主人公轮流操作，切换前遮挡隐藏信息；从引擎席位视图重新取数           |
| 保存与恢复 | 保存完整宿主局面并恢复到原等待点；玩家视图与完整宿主存档分开                     |
| 调试区域   | 查看实际与有效数值、当前能力、限次、来源和结算记录；记录命令序列用于复现         |
| 结局与重开 | 显示允许公开的结果；重新开始或加载另一剧本                                       |

如需补充“为什么不能发动”的信息，应由引擎提供原因并按席位过滤。隐藏身份或未公开规则的原因仅供全知调试查看。同机遮屏防止操作中误看，不承担对电脑所有者的防作弊职责。

完成标准：人工使用界面完成一局 First Steps；不需在过程中修改状态或运行命令补步骤；在行动选择、技能目标选择和跨轮节点退出恢复后能继续对局；各席位无意外隐藏信息泄露。

## P3：分批验收全部内容并补齐常驻整理

建议模组推进顺序为 First Steps → Basic Tragedy X → Midnight Zone → Mystery Circle → Haunted Stage Again → Weird Mythology → Another Horizon Revised → Last Liar。相同能力的验收结果可复用，模组差异仍单独验证。

角色按机制分批推进：普通指示物与移动；公开信息与身份；死亡、复活、保护和替代；间接使用技能与事件效果；特殊区域、EX、世界变化和跨轮效果。每一批同时核对角色特性与友好能力。

常驻整理与对应内容同批推进：明确来源、条件、依赖及覆盖顺序，逐步统一登记内置常驻；保留原始状态与有效状态的分离；为调试提供生效原因。需要按阶段检查的胜利条件继续按流程图时点检查。

每项能力围绕真实风险选择测试，覆盖适用的以下情况：

- 条件不满足、满足和后来失效；生效与撤销都正确。
- 合法目标、没有目标、多个目标，以及文本允许的自身、尸体、离场对象。
- 希望、绝望、里世界等对实际和有效数量的影响。
- 限次共享、拒绝、被中断、无变化但完成结算。
- 同时效果、获得其他身份能力、死亡触发和来源完成后续。
- 轮回重置、跨轮保留、保存恢复和公开信息。

跨规则组合优先覆盖实际冲突点：身份转换与死亡、获得关键人物能力与同时变化、保护与替代、技能完成后的连锁效果、常驻胜利与流程结束、范围替代与目标合法性。无需将所有理论组合穷举为同等优先级。

完成标准：P0 清单中所有计划支持条目专项测试通过，缺实现和已知错误清零；八模组各有合法剧本通过引擎整局和单机界面联调；尚有真实裁定歧义的内容不得标为支持完成。

## P4：正式单机 UI 与发布验收

功能稳定后完善版图和卡牌展示、中文技能说明、选中反馈、日志阅读、保存入口与错误提示。将调试信息收纳进调试模式，普通玩家界面只显示进行游戏所需内容。

把调试中发现的问题固化成可重复执行的回归场景。最终验收包含完整开发检查、代表性整局、关键等待点恢复、限次与跨轮清理、非法输入不改变局面，以及不同席位的信息边界。

完成标准：无需开发工具即可开局并完成游戏；支持范围、操作方式和已知限制有清楚说明；发布包可以启动、保存、恢复和结束对局。UI 美化完成不替代内容验收。

## P5：后续扩展

单机稳定后再安排联网房间、断线重连、服务器保存、多人权限，以及可选的电脑对手。现阶段保留已有命令与席位视图接口，为联网复用提供基础。

## 执行顺序与进度管理

P0 清单已交付，下一次实施从 P1 开始，先处理盘点确认的问题并产出 First Steps 验收结果，再进入 P2。P2 完成后用同一界面支持 P3 的逐批联调，P3 达标后进行 P4。

每批交付记录：核对了哪些规则、发现并修复了哪些问题、新增哪些结果断言、检查结果、仍未验收的条目和下一批范围。代码修改后执行与风险相符的专项测试，阶段交付执行 `run.ps1 check`。不以测试总数增长作为内容完成率。

当前只有快速核查，无法可靠给出缺失比例或工期。P0 得到实际缺口后再估算各批工作量；已经核对并通过验收的实现不重复开发。
